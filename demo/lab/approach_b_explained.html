1Stage 1 — same core as Approach A

Count characters, then repeatedly merge the most frequent adjacent pair inside pretok words until the vocab reaches BPE_SIZE (not the full 10k). Optional: EN unit frequencies × en_merge_weight so English subwords form more often. 

# approach_a/train_bpe.py — ClassicBPE.train (shared engine)
for step in range(target_merges):
    best_pair, best_freq = pair_counts.most_common(1)[0]
    a, b = best_pair
    new_tok = a + b          # e.g. "t"+"h" → "th"
    # apply merge inside every word; add new_tok to vocab
    self.merges.append(best_pair)
    self.vocab[new_tok] = len(self.vocab)

2Stage 2 — only Approach B

For every unique page word w, estimate how many pieces BPE needs today. Rank by how many tokens disappear if we store w whole: 

pieces(w) = len(bpe._encode_unit_dp(w))     # e.g. 3 for "maritime"
score(w)  = Σ_lang  α_lang · freq_lang(w) · max(0, pieces(w) − 1)

# Add highest score(w) into vocab until V = vocab_cap
for w, _ in scores.most_common():
    if len(bpe.vocab) >= vocab_cap: break
    if w not in bpe.vocab:
        bpe.vocab[w] = len(bpe.vocab)
Why “savings” not raw frequency? A short, frequent word like of may already be 1 BPE token → savings = 0. A long rare-ish word with 5 pieces saves 4 tokens every time it appears. Filling those first drops T (and English X) faster per vocab slot.

3Encode (same path A can use)

# for each pretok word w:
if w in vocab:                 # whole-word hit (B stage-2 gift)
    emit [w]
else:
    emit DP/min-merge cover of chars using merges   # pure BPE path

4. Approach A vs Approach B

A Pure BPE

chars + ~9800 merges → 10000

Entire budget spent on pair merges. A word is one token only if merges fully remix it. No explicit “insert page word” step.

B Optimized

~2500 BPE ~7500 whole words

Small BPE base + dump high-savings whole words. Encode prefers exact word matches first.

DimensionApproach AApproach B (optimized)
Vocab construction Only iterative pair merges until V Merges up to BPE_SIZE, then savings word fill to V
Goal of ranking types Pair frequency (merge stuff) Token savings if taken whole (fill stage)
Language balance knobs Implicit via data mass (EN dominates) α_lang + optional en_merge_weight
Typical literal budget (full page) ~200 chars + ~9800 merges ~200 chars + ~2300 merges + ~7500 words
Encode for known page word May still break into subwords Usually 1 token if it won a stage-2 slot
Encode for novel / OOV Subword merges Same subword path (stage-1 merges still apply)

5. Worked micro-example

Suppose pretok word maritime appears 12 times in EN.

cost = 3 tokens each occurrence
total cost on page ≈ 12×3 = 36 		maritime ∈ vocab
cost = 1 token each occurrence
total ≈ 12
savings score contribution = 12 × (3−1) = 24

Stage 2 compares this score against every other type (all langs × their α). Highest scores enter first until no slots left.

6. Why TE/SA used to show X = 1 under naive B

Unique types (full pages): EN≈7k, HI≈3.6k, TE≈2.2k, SA≈1.3k · union ≈12.6k > 10k.

If stage-2 fill used round-robin “give TE/SA every type first”, TE and SA inventories fit entirely inside 10k → every word encodes as 1 token → T = D → X = 1. EN still has ~3k leftover OOVs that explode → high X_EN.

Optimized B uses savings ranking (roughly uniform α), not “small language first”, so TE/SA are no longer guaranteed X=1; slots go to whatever reduces T most.

7. Metric reminder

D_lang  = # harness words on that language's India page
T_lang  = # tokens encode(page_lang) returns
X_lang  = T_lang / D_lang
score   = 1000 / (max X − min X)     # larger is better (tighter fairness)
hard_ok = (X_EN ≤ 1.2) and (vocab ≤ 10000)
